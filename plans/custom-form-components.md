# Plan: Custom dynamic Form components (SitecoreAI + Next.js front end)

## Context
The POC proves the front end ↔ SitecoreAI link with one `RichText` component. Goal: let authors build a form in SitecoreAI and have the Next.js app render it dynamically. The SDK's built-in `Form` (already in `.sitecore/component-map.ts`) only takes a `FormId` rendering param, fetches pre-rendered HTML from Edge client-side (`loadForm`), then sets `innerHTML` and executes its `<script>` tags. It works, but it is a black box: no custom markup, design system, validation or submit handling, and it runs injected scripts.

> **Status:** Option A (built-in `Form` + Sitecore Forms) is done and works with no front-end changes. This plan covers the move to custom forms (option B).

## Options

| | A. Built-in `Form` (Sitecore Forms) | B. Custom component, form as content items (recommended) | C. Hybrid: JSON schema field |
|---|---|---|---|
| Authoring | Sitecore Forms editor, pick `FormId` | Form template with child Field items (Text, Email, Select, Checkbox, ...) | One multiline/JSON field holding a schema |
| Rendering | Edge-delivered HTML, client-side | React, SSR via layout data | React, SSR |
| Styling/design system | Limited | Full | Full |
| Authoring UX / validation | Good | Good (typed items, Pages editing) | Poor (raw JSON) |
| Flexibility | Low | High | High, but hard to govern |
| Effort | None | Medium | Low-medium |

Recommendation: **B**, keeping A registered as a fallback for simple forms.

## SitecoreAI side (what to add)
1. **Templates** (under the site's Data/Templates, deploy via serialization):
   - `Form` : Title, SubmitLabel, SuccessMessage, ErrorMessage, optional `Action` key (which backend handler), Consent text.
   - `Form Field` base : Name (machine key), Label, Required, HelpText, ErrorMessage.
   - Field-type templates inheriting the base: `Text`, `Email`, `TextArea`, `Select` (+ `Option` children), `Checkbox`, `Radio`, `Hidden`. Type-specific params only (placeholder, min/max, pattern chosen from an allowed list, never free regex from the client).
2. **Rendering/component definition** `Form` in the Components builder: datasource template = `Form`, datasource-required. Optionally a placeholder-based variant for layout of field groups.
3. **Item hierarchy**: form datasource item → child field items (ordered by sort order). Create under site Data folder; add insert options so authors can only add allowed field types.
4. **Delivery**: make sure the datasource and children are published to Edge. Children of a datasource are reachable via the layout `fields` (`items`) or one GraphQL query in `getComponentData`.
5. **Editing**: add the component to a page's placeholder in Pages and confirm in editing mode.

## Front-end side (what to add)
1. `src/components/Form/Form.tsx`: a custom component, registered as e.g. `ContactForm` to avoid colliding with the SDK `Form` key (map is regenerated by `sitecore-tools:generate-map`).
2. **Data**: export `getComponentServerProps` from the component to fetch child fields via GraphQL with `client` from `src/lib/sitecore-client.ts` (reuses the existing `getComponentData` call in `[[...path]].tsx`); pass only serializable, whitelisted props.
3. **Field registry** `src/components/Form/fields/index.ts`: map template name → React field component (`TextField`, `EmailField`, `SelectField`, ...). Unknown types render nothing (and log in editing). Adding a field type = one component + one registry line + one template.
4. **Schema + validation**: convert items to a normalized `FormSchema` (zod). Use the same schema on the client (UX validation) and the server (authoritative).
5. **State**: small client component using native form + `useActionState`/controlled state; accessible labels, `aria-invalid`, `aria-describedby`; use SDK `<Text>`/`<RichText>` for authored copy so it stays editable in Pages.
6. **Submission**: `src/pages/api/forms/submit.ts` (add rewrite in `next.config.js` and keep proxy matcher in sync per AGENTS.md). Handler looks up the form by id from Sitecore (server-side), re-validates against the schema, then forwards to the configured destination (email service, CRM, Sitecore CDP/Forms, webhook).
7. Editing-safe rendering: no submit/network calls when `page.mode.isEditing`; follow `content-sdk-editing-safe-rendering` skill.

## Flexibility
- Schema-driven: authors add/reorder/remove fields with no deploy.
- Field registry makes new types additive; `Action` key selects a registered handler (`handlers/email.ts`, `handlers/webhook.ts`).
- Rendering param `Styles` / variants for layout themes; conditional visibility (`showIf` field name/value) as a later extension.
- Dictionary items for built-in messages (i18n) via existing dictionary support.

## Security
- Never trust the client: server re-fetches the form definition by id and validates only against it; reject unknown fields, enforce max lengths/sizes.
- Destination URLs, API keys and secrets live in env vars on the server; authors choose only an `Action` key from an allowlist (prevents SSRF/open relay). Nothing secret in `NEXT_PUBLIC_*`.
- Rate limiting + honeypot field (and optional CAPTCHA/Turnstile) on the API route; CSRF: same-origin check + SameSite, Origin header verification.
- No `dangerouslySetInnerHTML` of author content except through SDK `<RichText>`; escape all output; avoid built-in `Form`-style script injection for custom forms.
- Don't log PII; minimize retention; consent checkbox and privacy text stored as authored content.
- Authoring-side: restrict who can edit form templates/items via Sitecore roles; limit insert options.

## Suggested phases
1. Templates + datasource + one field type (Text) rendered end-to-end.
2. Field registry (Email, TextArea, Select, Checkbox, Radio, Hidden) + zod schema.
3. Submission API + one handler (webhook/email) with validation, rate limit, honeypot.
4. Editing-mode polish, i18n, a11y, variants.

## Verification
- `npm run type-check` and `npm run lint`; `npm run build` regenerates the component map with the new component.
- `npm run dev`: create form in Pages, confirm SSR HTML contains fields, editing mode shows no submits.
- Submit valid payload (success), invalid/extra fields (400), oversized, repeated bursts (429); confirm secrets absent from client bundle (`.next/static`).
- Unit tests (if added) for schema conversion and field registry fallback.
